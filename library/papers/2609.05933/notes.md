# Rethinking the Evaluation of Efficiency Methods for Multi-Agent Systems

- arXiv 2609.05933v1 · 발표 2026-09-05 · cs.LG · **EMNLP 2026 Outstanding Paper** (공식 수상 페이지 확인, 2026-11-14) · Jiamu Zhang 외 (Rice University, Case Western Reserve University — 본문 저자 표기)
- 변환 html · 읽은 범위: 1 Introduction ~ Limitations (부록 안 읽음)
- 정리 2026-11-14 KST

## 먼저 — 용어와 구조
- **MAS = Multi-Agent System.** 이 논문의 MAS: 같은 모델(4B~8B)에 역할 프롬프트만 다른 LLM 에이전트 6개가 각자 컨텍스트를 갖고,
  정해진 연결 구조(Star·완전연결·Chain·Layered·Random)를 따라 서로의 답을 읽으며 2라운드 → 집계 에이전트가 최종 답. 토론·앙상블형.
- **단일 에이전트:** 컨텍스트 1개짜리 LLM. 도구를 여러 개 쓰는 ReAct 도 단일 에이전트다 (MAS 를 가르는 건 도구 수가 아니라
  "별도 컨텍스트의 LLM 이 여럿이고 그 사이에 메시지가 오가는가"). 이 논문의 기준선은 도구 루프 없는 호출 1회로 보임.
- **가지치기(pruning):** MAS 의 연결선을 지우기(호출은 하되 상대 프롬프트에 안 넣음 — AgentPrune·GPTSwarm) 또는 에이전트를 지우기
  (아예 호출 안 함 — AgentDropout), 질문마다 다르게(AGP·DAGP). 무엇을 지울지는 학습용 질문으로 MAS 를 반복 실행해
  "정답이 나온 실행에 있던 연결"의 확률을 올리는 강화학습(REINFORCE)으로 정한다 (부록 B).
- 작업을 나눠 맡기는 **오케스트레이터형**(서브에이전트) MAS 와는 다르다 — 이 논문 결론을 그쪽에 그대로 옮기지 말 것.

## 결론
**멀티에이전트(MAS) "효율화" 연구들의 성과 상당수는 방법의 효과가 아니라 실험 조건의 효과였다. 조건을 통일하면 학습된 가지치기가
무작위 가지치기와 거의 구분되지 않는다.**
- **가져갈 것:** 비교 실험의 두 가지 함정과 그 대조군 — ① 조건이 다른 보고값끼리 비교하지 말 것(모델·프롬프트·에이전트·런타임 고정),
  ② **"이 설정이 애초에 그 구조를 필요로 하는가"를 확인하는 대조군**(같은 예산의 무작위 제거, 단일 에이전트 기준선)을 반드시 둘 것.
  그리고 비용 지표를 하나만 보지 말 것 — 엣지 토큰은 줄어도 실제 청구되는 프롬프트 토큰은 늘 수 있다.
- **믿어도 되는 결과:** 같은 예산 무작위 제거 대비 정확도 −0.77 vs −0.44, 이긴 경우 12/25 (≈ 반반) — 표 2. 실행 간 표준편차 0.6~2.1점이
  대부분의 보고된 향상과 같은 크기 — E 부록 요약(본문 4.2). 설계(한 번에 한 축만 바꾸는 38칸 격자)가 탄탄하다.
- **해석에 주의할 결과:** 4B~8B 소형 모델만 썼고, 각 방법의 원래 프롬프트를 걷어냈다 — 저자도 "강한 모델이나 원래 프롬프트에서는 다를 수
  있다"고 인정. 무작위 대조군은 예산당 1회 샘플, 신뢰구간은 MMLU 한 과제만. "기존 방법이 쓸모없다"가 아니라 "**기존 평가로는 알 수 없다**"로 읽어야 한다.
- **읽는다면:** 1장(문제 제기 두 가지), 3.3절(한 축씩 바꾸는 격자·비용 지표 두 개), 4.2절의 표 1·2와 "Matched random pruning" 단락.
- **논문 주장과 내 해석 구분:** 논문의 주장은 "효율화 평가가 제각각이라 판정 불가 + MAS 가 필요한 설정에서 평가해야 함 +
  어떻게 줄였나를 봐야 함". **"단일 에이전트로 충분하다/MAS 는 불필요하다"는 논문 주장이 아니다** — 저자는 "MAS 를 써야 하나"를
  보완적 질문으로 범위 밖에 둔다(2장). 단일 대비 MAS 효용이 낮다는 건 표 1 에서 내가 계산한 것이고, 4~8B·토론형·도구 없음·4과제 범위.
- **범위 주의:** 여기서 MAS 는 **같은 모델에 역할 프롬프트만 다른 LLM 호출 6개가 연결 구조를 따라 서로 답을 읽는 토론·앙상블형**이다
  (도구 쓰는 ReAct 에이전트는 에이전트 1개). 작업을 나눠 맡기는 오케스트레이터형(서브에이전트)에 결론을 그대로 옮기면 안 된다.
  단일 에이전트 기준선은 도구 루프 없는 LLM 호출 1회로 보임 (GSM8K 0.07K 토큰 — 구현은 부록, 확인 안 함).
  다수결(self-consistency) 기준선과는 비교하지 않았다 (읽은 범위).

## 한 줄 요약
MAS 를 가지치기해 비용을 줄인다는 방법 5개를 같은 모델·에이전트·런타임에서 다시 돌려 보니, 성과가 시작 구조에 따라 들쭉날쭉하고
같은 예산의 무작위 제거와 별 차이가 없었다.

## 문제와 핵심 아이디어
- 효율화 방법들(AgentPrune·AgentDropout·AGP·DAGP·GPTSwarm)은 각자 다른 프롬프트·에이전트 클래스·시작 그래프·백본·비용 계산법으로 보고했다
  → 향상이 방법 덕인지 설정 덕인지 알 수 없다.
- 더 근본적으로, **애초에 멀티에이전트가 필요 없는 설정**에서 평가하면 무엇을 지워도 성능이 유지된다 → "잘 지웠다"가 아니라 "지워도 되는 걸 지웠다".
- 해법: MAS 를 (토폴로지, 에이전트 배정, LLM, 방법별 하이퍼파라미터) 4-튜플로 정의하고 앞 셋을 고정. 토폴로지는 공간(같은 라운드 내 전달)·
  시간(라운드 간 전달)·노드(활성 여부) 세 마스크로 분리. 역할을 노드 번호에 고정해 노드가 빠져도 프롬프트가 밀리지 않게 함.
- 평가 격자: 기준 설정(Star, 6 에이전트, 2 라운드, 도구 없음)에서 **한 번에 한 축만** 바꾼 38칸 (토폴로지 5종·에이전트 수·라운드·도구).
  과제 4개(GSM8K, MMLU-500, HumanEval, LiveCodeBench-150), 백본은 과제별 고정(Qwen3-4B / Llama-3.1-8B / Qwen2.5-Coder-7B).

## 저자 주장
- 어떤 방법도 시작 토폴로지에 걸쳐 일관되지 않다. 최선 방법이 과제·토폴로지마다 바뀐다. DAGP 가 가장 안정적 — 표 1, 4.2절
- 같은 예산 무작위 제거 대비: 방법 평균 −0.77점 vs 무작위 −0.44점, 정확도 우위 12/25. 뚜렷한 우위는 DAGP 뿐(4/5) — 표 2
- 가지치기 후 오히려 비싸지는 경우: 결정 노드를 덧붙이는 설계 때문에 엣지는 줄어도 프롬프트 토큰 증가 (AgentPrune/Star/GSM8K +2.83K) — 4.2절
- 실패 유형 세 가지: 병목 엣지 제거로 붕괴(GPTSwarm/Chain/GSM8K −86.27점), 집계 노드 오버헤드, 그래프 붕괴(AGP/Random/HumanEval −17.39점) — 표 3
- 성공 사례의 공통점: 핵심 추론·결정 경로는 두고 중복 노드-라운드만 조금 제거 — "얼마나 줄였나"보다 "어떻게 줄였나" — 4.2절
- 도구가 있는 설정에서는 실행·검색 에이전트를 꺼서 비용을 줄이는 경우가 있다 — 그건 효율화가 아니라 도구 경로 제거 — 4.2절
- GPTSwarm 은 38칸 중 13칸에서 노드·엣지 수는 그대로 두고 역할만 뒤섞었다 — 3.1절
- 실행 간 표준편차 0.6~2.1점 = 보고된 향상 대부분과 같은 크기. 유의한 구간은 과도하게 연결된 FC 토폴로지뿐 — 4.2절(부록 E.2 요약)

## 실험에서 볼 것
- **단일 에이전트 기준선이 강하다 (표 1, 내가 계산).** 정확도/프롬프트 토큰(K): GSM8K 단일 89.76/0.07 vs Star MAS 94.62/11.90,
  MMLU 70.80/0.18 vs 72.40/5.97, HumanEval 83.23/0.21 vs 85.71/10.78, LiveCodeBench 50.00/0.57 vs 50.00/17.42.
  → 이 설정에서 MAS 는 프롬프트 토큰 약 30~170배를 써서 정확도 **−4 ~ +4.9점** (구조 5종 범위).
  GSM8K 는 모든 구조에서 +2.6~+4.9, LiveCodeBench 는 5개 중 4개 구조에서 단일보다 **낮음**(0 ~ −4), MMLU·HumanEval 도 완전연결에선 단일보다 낮음.
  (토큰은 입력만·공백 기준 근사·중복 계산된 상한 — 3.3절. 출력 토큰·지연 시간은 읽은 범위에 없음.
  지연은 구조상 추정: 순차 단계 수 Star ≈ 4~5, Chain ≈ 12, 완전연결 ≈ 2~3 — 병렬 실행 가정, 측정 아님)
- 각 방법의 공식 구현·학습 알고리즘은 그대로, 주변 하네스만 통일. 논문과 코드가 다른 경우 어느 쪽을 돌렸는지 부록 B 에 기록했다고 함 (확인 안 함).
- 적응형 방법(AGP·DAGP)은 질의별 마스크를 하나의 고정 토폴로지로 증류해 평가 — 질의별로 돌려도 결론 같다고 부록 E.1 (확인 안 함).

## 한계
- 논문이 밝힌 것: 기존 MAS 를 고치는 방법만 대상(처음부터 만드는 방법 제외) / 과제 4개 + HotpotQA, 장기 계획·상호작용 환경 없음 /
  신뢰구간은 MMLU 만, 무작위 대조는 예산당 1회 / 4B~8B 소형 모델만 / 공유 프롬프트로 각 방법의 프롬프트 엔지니어링 제거 / 영어만, 비용은 근사.
- 읽으며 본 것 (내 판단): 비판 대상 방법들에 불리할 수 있는 조건(소형 모델·원래 프롬프트 제거)을 저자가 정했다 — 저자도 인정하지만,
  "통제"와 "방법이 의도한 조건" 사이의 긴장은 남는다. 이 논문의 결론도 이 조건 안에서의 결론.

## 관심 주제와의 연결
- **multi-agent evaluation / 평가 설계:** 직접 해당. "한 번에 한 축만 바꾸기", "같은 예산 무작위 대조군", "단일 에이전트 기준선",
  "비용 지표 두 개"는 어떤 에이전트 구조 비교에도 그대로 쓸 수 있는 평가 설계 체크리스트.
- **LLM agent / agent harness:** 실무 시사점 — 멀티에이전트를 쓰기 전에 단일 에이전트 기준선부터. 이 논문 설정에서는 토큰 30~170배로 −4~+4.9점.
  "Free to Look"(단순 하네스가 수작업 파이프라인보다 낫다)·Meta-Harness 와 같은 방향의 근거.
- **LLMs Get Lost 와의 연결:** 둘 다 "평균 하나"를 믿지 말라는 논문 — 저쪽은 실행 간 편차를, 이쪽은 실행 간 편차(0.6~2.1점)가 보고된
  향상과 같은 크기임을 보였다.

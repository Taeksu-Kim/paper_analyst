# LLMs Get Lost In Multi-Turn Conversation

- arXiv 2505.06120v1 · 발표 2025-05-09 · cs.CL · **ICLR 2026 Outstanding Paper** (공식 블로그, 웹 검색으로 확인) · Laban 외 (소속 확인 안 함 — 코드는 microsoft GitHub)

## 결론
**"모델이 멍청해지는 게 아니라, 매번 다른 답을 내게 된다." 멀티턴에서 성능이 떨어지는 원인 대부분은 능력이 아니라 신뢰도(실행 간 편차)다.
그리고 흔히 쓰는 처방(온도 0, 대화 요약 반복)으로는 잘 안 고쳐진다.**
- **가져갈 것:** 성능을 평균 하나로 보지 말고 **같은 입력을 N번 돌려 Aptitude(상위 10% 점수) / Unreliability(상위 10%−하위 10% 점수 차)로 쪼개는 지표.**
  실행마다 흔들리는 생성물을 평가할 때 그대로 쓸 수 있는 정의다.
- **믿어도 되는 결과:** 15개 모델 × 600개 지시 × 10회 반복(20만+ 대화)에서 **모든 모델·모든 과제**가 떨어졌다. 정보 손실이 원인이 아님을
  Concat 대조군(같은 정보를 한 번에 주면 Full 의 95.1%)으로 배제했다 — 통제가 잘 된 실험.
- **해석에 주의할 결과:** 원인을 "모델의 신뢰도 문제"로 본 해석에는 반론이 나왔다 (Intent Mismatch, 2026.02 — 사용자 의도 정렬 문제이며
  중개자 구조로 상당 부분 회복). 또 사용자 시뮬레이터가 GPT-4o-mini 라 실제 사람과의 대화를 대표하지 않는다 (저자도 인정).
- **읽는다면:** 3.3절(시뮬레이션 유형 5가지 — 대조군 설계), 4.2절(지표 정의), 6.2절(능력 vs 신뢰도), 7.1~7.2절(처방 실험). 이 4곳이면 충분.

## 한 줄 요약
같은 과제를 한 번에 다 주면 90% 를 하던 LLM 들이, 정보를 여러 턴에 나눠 주면 평균 39% 떨어지며, 그 하락은 대부분 능력이 아니라 실행 간 편차(신뢰도) 증가에서 온다.

## 문제와 핵심 아이디어
- 실제 사용자는 처음에 지시를 덜 구체적으로 주고 대화하며 채워 간다(underspecification). 그런데 평가는 거의 다 "한 번에 다 주는" 단일 턴이거나,
  턴마다 독립 과제인 "에피소드형" 멀티턴이다 — 정보를 **합쳐서** 답해야 하는 상황을 안 잰다.
- **Sharding:** 기존 단일 턴 벤치마크의 지시를 "의도 1개 + 조건 여러 개" 조각(shard)으로 쪼개고, LLM 사용자 시뮬레이터가 턴마다 한 조각씩 공개.
  같은 과제를 단일 턴(Full)·조각 합친 단일 턴(Concat)·멀티턴(Sharded)으로 돌려 **같은 과제 위에서** 비교한다.
- 과제 6개(코드, SQL, API 호출, 수학, 표→문장, 다문서 요약), 15개 모델, 온도 1.0, 지시당 10회 반복 → 약 $5,000.

## 저자 주장
- 모든 모델이 모든 과제에서 Full → Sharded 하락, 평균 **−39%** (상대) — 6.1절, 표 1. 서론 기준 절대값으로는 약 90% → 65%
- Concat 은 Full 의 95.1% → 하락 원인은 쪼개면서 생긴 정보 손실이 아님 — 6.1절
- 강한 모델(Claude 3.7 Sonnet, Gemini 2.5, GPT-4.1)도 약한 모델만큼 길을 잃음 (30~40% 하락) — 6.1절
- 추론 모델(o3, R1)도 똑같이 무너짐. 답이 33% 더 길고, 긴 답일수록 가정이 많이 섞임 — 6.1절
- **Aptitude 는 평균 16% 하락, Unreliability 는 112% 증가(2배 이상).** 같은 지시에서 최고·최악 실행 차이가 평균 50%p — 6.2절
- 2조각 이상으로만 나눠도 길을 잃음 (조각 수 1~8 실험, GPT-4o/4o-mini) — 6.3절
- 처방: 매 턴 이전 정보를 다시 말해 주는 Snowball 은 하락의 15~20% 만 회복, 마지막에 몰아서 요약(Recap)은 더 낫지만 비현실적 — 7.1절, 표 2
- 온도 0: 단일 턴은 편차가 50~80% 줄지만, 멀티턴은 거의 안 줄고 약 30% 편차가 남음 — 7.2절, 표 3
- 원인 4가지: 너무 일찍 완성 답을 냄 / 이전의 틀린 답에 의존 / 첫·마지막 턴만 반영(중간 턴 손실) / 장황한 답 — 6.2절, 부록 F
- 번역처럼 턴별로 쪼개지는(에피소드형) 과제는 하락 없음 — 7.3절, 표 4

## 실험에서 볼 것
- **대조군 설계가 좋다.** Concat 으로 "쪼개는 과정의 정보 손실"을, 번역 과제로 "에피소드형이면 괜찮다"를 각각 배제·확인했다.
- 사용자 시뮬레이터·응답 분류·답 추출이 모두 GPT-4o-mini. 수작업 점검에서 오류 5% 미만, 평가 대상에 불리한 오류 2% 미만이라고 보고 (부록 D, 확인 안 함).
- 사용자 시뮬레이터는 **매 턴 반드시 새 정보를 주고, 마지막엔 정보가 다 갖춰지는** 이상적 조건 — 저자는 그래서 실제보다 과소평가라고 주장.
- 처방 실험(Recap·Snowball·온도)은 GPT-4o/4o-mini 두 모델, 일부 과제만.

## 한계
- 논문이 밝힌 것: 자동 시뮬레이션이라 실제 사람 대화를 대표하지 않음 / 분석형 과제만 (창작 제외) / 영어 텍스트만.
- 읽으며 본 것 (내 판단): 시스템 프롬프트로 "질문해도 된다"는 등의 전략을 **일부러 주지 않았다** (기본 행동을 보려는 설계) —
  실제 제품은 이런 지시를 주므로, 프롬프트·하네스 설계로 얼마나 회복되는지는 이 논문이 답하지 않는다.

## 관심 주제와의 연결
- **multi-agent evaluation / 평가 설계:** Aptitude(P90)·Unreliability(P90−P10) 지표는 "실행마다 흔들리는 결과를 여러 번 돌려 비교"하는 평가에
  바로 쓸 수 있는 정의. 평균만 보면 "능력이 떨어졌다"와 "들쭉날쭉해졌다"가 구분되지 않는다.
- **LLM agent / agent harness:** 저자는 "하네스(요약 반복)로는 15~20% 만 회복 → 모델이 해결해야" 라고 주장하지만, 후속 연구(Intent Mismatch,
  Agentic Context Management)는 하네스 쪽 처방(입력 재작성·컨텍스트 관리)이 꽤 통한다고 반박 중 — **아직 열린 쟁점**.
- **context compaction:** "턴이 쌓일수록 이전의 틀린 시도가 오염원이 된다"는 관찰은 압축·리셋 설계의 근거 (SWE-MeM 의 "깨끗한 작업 컨텍스트"와 같은 방향).

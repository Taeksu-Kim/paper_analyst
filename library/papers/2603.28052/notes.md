# Meta-Harness: End-to-End Optimization of Model Harnesses

- arXiv 2603.28052v1 · 발표 **2026-03-30** · cs.AI · 학회 미확인 (S2 venue = arXiv) · Yoonho Lee, Roshen Nair, Qizheng Zhang, Chelsea Finn (Stanford) · Kangwook Lee (KRAFTON) · Omar Khattab (MIT) — HTML 저자 표기 확인. KRAFTON AI API 크레딧 지원
- 변환 html · 읽은 범위: 1~5장 전체, 부록 B.1(분류 하네스)·B.3(TerminalBench 하네스)·D(구현 팁)
- 정리 2026-11-14 KST

## 먼저 — 용어와 구조
- **하네스(harness):** 고정된 LLM 을 감싸는 코드 — 무엇을 저장하고, 무엇을 검색하고, 매 단계 모델에게 무엇을 보여줄지 정하는 프로그램.
  프롬프트 구성·검색·메모리·도구 호출 로직 전부. 이 논문에서는 **파이썬 파일 1개**. 같은 모델이라도 하네스에 따라 성능이 6배까지 차이 난다고 인용.
- **Meta-Harness:** 하네스를 자동으로 개선하는 바깥 루프. 제안자(proposer) = **Claude Code(Opus 4.6)**.
  ```
  ① 파일시스템에 지금까지의 모든 후보 하네스의 [코드, 점수, 실행 기록 원본]이 디렉터리별로 쌓여 있음
  ② Claude Code 가 grep·cat 으로 필요한 것만 골라 읽고 (반복당 중앙값 82개 파일) → 실패 원인 가설 → 새 하네스 코드 작성
  ③ 간단한 검증 테스트 통과하면 → 바깥 스크립트가 평가 → 결과를 새 디렉터리로 저장 → 반복 (보통 20회, 후보 약 60개)
  ```
  모델 가중치는 안 건드린다 (기반 모델 고정). 기존 프롬프트 최적화(GEPA·OPRO·TextGrad)는 점수나 요약만 보는데, 이건 **실행 기록 원본 전체**를 본다.

## 결론
**"하네스 개선을 사람 대신 코딩 에이전트에게 맡기되, 요약이 아니라 실행 기록 원본을 파일로 열어 주면 사람이 만든 최고 하네스를 넘는다."
핵심 변수는 탐색 알고리즘이 아니라 '제안자가 무엇을 볼 수 있나' — 원본 기록을 주면 중앙값 50.0, 점수만/요약만 주면 34.6/34.9.**
- **가져갈 것:**
  ① 개선 루프 설계 — 후보마다 [코드·점수·원본 trace] 디렉터리, 제안자는 Claude Code + 짧은 스킬, 검증 테스트로 깨진 후보 걸러내기,
  평가는 제안자 밖 스크립트, 탐색용 문제는 **기준선이 틀리는 것 위주 50~100개**. "스킬 문구를 다듬는 게 반복 횟수·후보 수보다 효과가 컸다"(부록 D).
  ② **요약을 주지 말고 원본 trace 를 줘라** — LLM 요약은 진단에 필요한 세부를 지워서 오히려 손해 (표 3).
  ③ 찾아낸 하네스 패턴 3개 (학습 없이 바로 시험 가능):
     - **초안 → 검증:** 초안 답을 내고, 그 답과 같은 라벨의 예(지지)와 다른 라벨의 예(반박)를 다시 검색해 보여 주고 유지/수정 판단 (짧은 호출 2번)
     - **라벨 공간 먼저:** 가능한 라벨 전체 목록 + 라벨별 대표 예 1개 + 질의 근처의 "비슷한데 라벨이 다른" 쌍을 한 프롬프트에
     - **환경 스냅샷:** 에이전트 루프 전에 작업 환경(디렉터리·설치된 언어·패키지 관리자·메모리)을 한 번에 수집해 첫 프롬프트에 넣음
       → 탐색에 쓰던 2~4턴 절약, 80줄. 이득은 "환경이 뻔하지 않은 과제"에서 컸음
- **믿어도 되는 결과:** 분류(표 2, OOD 9개 데이터셋 표 5)와 수학 검색(처음 보는 모델 5종, 표 6)은 **탐색 세트와 테스트 세트를 분리**했다.
  원본 trace 의 효과(표 3)는 같은 조건 비교.
- **"사람보다 낫다"의 실체 — 사람 기준선의 수준이 영역마다 다름:**
  - 분류: **기준선이 약함.** "최신" 수작업 하네스 ACE 40.9·MCE 40.0 이 예시 전부 넣는 few-shot 40.8 과 같거나 낮음 (컨텍스트는 2~4배).
    ACE·MCE 는 원저자가 아닌 MCE 저자 구현(†). 향상은 Law(+16)에 몰려 있고 USPTO 는 오히려 낮음(14.0 vs 16.0). OOD 9개는 +2.9.
  - 수학 검색: 기준선이 단순 설정 — 헤드라인 +4.7 은 "검색 없음" 대비, **BM25 대비로는 +1.3** (200문제 중 2~3문제).
  - TerminalBench: 기준선은 강하지만 **사람 최고 하네스(Terminus-KIRA)에서 출발해 80줄 추가**, +1.7%p. 사람 최고(ForgeCode 81.8)는 못 넘음.
  - → 정확한 표현: "사람보다 잘 만든다"가 아니라 "사람이 만든 출발점을 자동으로 조금 더 개선, 기준선이 약한 곳에선 크게". 같은 예산의 사람 엔지니어와 직접 비교는 없음.
- **해석에 주의할 결과:** TerminalBench-2 는 **탐색과 최종 평가를 같은 89개 과제로** 했다 (저자도 명시, "발견 문제"로 취급). 후속 비판 논문
  (*Rethinking the Evaluation of Harness Evolution for Agents*, 2607.12227)은 탐색·평가를 분리하면 하네스 진화의 이득이 미미하고
  병렬 샘플링·순차 개선과 비슷하다고 주장 (초록 기준, Meta-Harness 를 직접 시험했는지 확인 안 함). 또 제안자가 최상위 모델(Opus 4.6)이라 비용이 크고,
  다른 제안자에서의 효과는 저자도 미검증.
- **읽는다면:** 1장, 3장(루프 설계), 표 3(무엇을 보여 주나 실험), 부록 B(찾아낸 하네스), 부록 D(구현 팁).

## 한 줄 요약
코딩 에이전트에게 과거 하네스들의 코드·점수·실행 기록 원본을 파일로 열어 주고 하네스 코드를 고치게 했더니, 분류·수학 검색·터미널 코딩에서 사람이 만든 하네스를 넘었다.

## 문제와 핵심 아이디어
- 하네스 엔지니어링은 여전히 수작업 — 실패 보고, 규칙 고치고, 몇 개 설계를 반복.
- 기존 텍스트 최적화 기법은 피드백을 너무 압축한다 (현재 후보만, 점수만, 요약만) — 반복당 0.002~0.026M 토큰.
  하네스는 "무엇을 저장할지" 같은 결정이 여러 단계 뒤에 영향을 미쳐서, 압축된 피드백으로는 원인 추적이 안 된다.
- 해법: 전체 이력을 파일시스템으로 노출 (평가 한 번에 최대 1,000만 토큰의 진단 정보) + 코딩 에이전트가 골라 읽기.
  탐색 구조(부모 선택 규칙 등)는 일부러 최소화 — "코딩 에이전트가 강해지면 자동으로 좋아지게".

## 저자 주장
- 온라인 텍스트 분류(GPT-OSS-120B): 48.6% — ACE 대비 +7.7, MCE 대비 +8.6, 컨텍스트 11.4K (ACE 50.8K, MCE 28.5K) — 표 2
- 같은 평가 예산에서 OpenEvolve·TTT-Discover 의 최종 성능을 **평가 횟수 1/10** 로 따라잡고, 최종 정확도는 10점 이상 높음 — 4.1절, 표 4
- 처음 보는 분류 데이터셋 9개: 평균 73.1% (ACE 70.2%). few-shot 을 32개 넘게 늘리면 9개 중 7개에서 오히려 하락 — 표 5
- 올림피아드 수학 + 50만 문제 검색: 찾아낸 검색 하네스 하나가 처음 보는 모델 5종 평균 +4.7점 (BM25 대비 +1.3). 밀집 검색·무작위 few-shot 은 일부 모델에서 하락 — 표 6
- TerminalBench-2: Opus 4.6 76.4% (Terminus-KIRA 74.7%, Opus 4.6 중 2위), Haiku 4.5 37.6% (Haiku 중 1위). 1위 ForgeCode(81.8%)는 공개 코드로 재현이 안 됐다고 주장 — 표 7
- 제안자의 행동: 구조 수정과 프롬프트 수정을 같이 넣었다가 둘 다 나빠지자, "공통으로 넣은 프롬프트 수정이 원인일 수 있다"고 가설을 세워 분리하고 더 안전한 추가형 수정으로 전환 — 4.3절, 부록 A.2(안 읽음)
- 탐색 한 번에 몇 시간, 결과 하네스는 읽을 수 있는 코드라 과적합(하드코딩된 if 문 등)도 눈으로 확인 가능 — 5장

## 실험에서 볼 것
- 비교 대상 텍스트 최적화 기법들도 **같은 제안자(Opus 4.6)와 같은 평가 예산**으로 돌림 — 공정한 편. Best-of-N(구조 없는 독립 샘플)도 대조군으로 둠.
- 분류·수학은 탐색 세트와 테스트 세트 분리, 수학 검색 코퍼스는 중복 제거·오염 검사(부록 C.2, 안 읽음).
- TerminalBench 는 탐색=평가. 과적합은 수작업 점검과 정규식 감사로 확인했다고 함. 이득은 89개 중 7개 과제에서 — 차이 1.7%p(Opus)는 1~2문제 수준.
- 반복 실행·분산 보고는 읽은 범위에서 못 봄 (수학은 문제당 3회 평균).

## 한계
- 논문이 밝힌 것: 제안자는 Claude Code(Opus 4.6) 하나로만 시험 / 하네스와 모델 가중치 공동 진화는 향후 과제.
- 읽으며 본 것 (내 판단): 제안자 비용(Opus 4.6 로 20회 × 반복당 수십 개 파일)과 평가 비용(후보 60개 × 탐색 세트)이 커서,
  작은 팀이 돌리려면 탐색 세트를 작게(50~100개) 잡아야 한다 — 저자 권고와 같은 방향. 깨끗한 하네스 인터페이스와 믿을 만한 평가 세트가 전제.

## 관심 주제와의 연결
- **agent harness:** 직접 해당. 운영 중인 대화형 에이전트의 개선 루프(trace → triage → 수정 → 재현·회귀 → 사람 승인)를 코딩 에이전트로
  자동화하는 설계도. 차이는 "요약 대신 원본 trace 디렉터리를 준다", "스킬 문구가 가장 큰 레버", "탐색 세트는 기준선이 틀리는 것 위주".
- **agent skills:** 제안자를 조종하는 인터페이스가 스킬 — "진단 절차는 강제하지 말고 금지 사항·산출물·목표만 정하라"(부록 D).
  paper_analyst 스킬 설계에도 같은 원칙.
- **RAG:** 수학 검색에서 "검색을 붙이느냐"보다 "검색 정책"이 중요 — 밀집 검색(k=1)·무작위 few-shot 은 오히려 하락할 수 있다.
  "초안 → 지지·반박 예 검색 → 판단"은 RAG 답변 검증에도 옮길 수 있는 패턴.
- **LLMs Get Lost 와의 연결:** 환경 스냅샷 하네스의 이득이 "초반의 잘못된 가정이 연쇄되는 과제"에서 컸다 (부록 B.3) —
  `ideas/2026-11-14_multiturn_scope_first.md` 의 "범위·상태를 먼저 확정" 설계와 같은 방향.

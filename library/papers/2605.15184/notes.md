# Is Grep All You Need? How Agent Harnesses Reshape Agentic Search

- arXiv 2605.15184v1 · 발표 **2026-05-14** · cs.CL · 학회 미확인 · Sahil Sen 외 4인 — **5명 모두 PricewaterhouseCoopers, U.S.** (HTML 저자 표기 확인)
- 변환 html · 읽은 범위: 1~6장 전체 (부록 A 안 읽음)
- 정리 2026-11-15 KST

## 먼저 — 용어와 구조
- **범위:** 일반 검색이 아니다. **LongMemEval** (한 사용자와의 여러 세션 대화 기록으로 질문에 답하기) 116문항, **질문마다 전용 대화 묶음 파일**
  (세션 39~66개) 안에서만 검색. 대화 턴 + 전처리(Chronos)가 뽑은 정규화된 시간 이벤트 기록이 검색 대상.
- **grep 도구:** 파일을 메모리에 올려 정규식 매칭, 매칭 수로 정렬해 반환 (임베딩·인덱스 없음). 검색어(패턴)는 **에이전트가 만들고 고친다**.
- **벡터 도구:** 턴·이벤트를 임베딩, 근사 최근접 검색 → 재정렬 → 상위 k (k 는 에이전트가 정함).
- **하네스:** 자체 하네스 Chronos(LangChain, 질문 유형별 동적 프롬프트) vs 제공사 CLI (Claude Code·Codex·Gemini CLI, bash 로 검색 스크립트 호출).
- **결과 전달 방식:** 바로 넣기(inline, 도구 결과를 대화에) vs 파일(programmatic, 결과를 파일로 쓰고 에이전트가 읽음).
- 채점: GPT-4o 이진 판정 (LongMemEval 규약).

## 결론
**근거가 원문 그대로 있는 작은 범위(한 사람의 대화 기록)에서는, 에이전트가 패턴을 만들어 다듬는 문자 매칭(grep)이 벡터 검색보다 정확했다.
하지만 결과 전달 방식·하네스를 바꾸면 순위가 뒤집히고, 하네스 차이가 검색 방식 차이만큼 크다.**
- **가져갈 것:** ① **넓은 범위는 의미 검색으로 좁히고, 좁힌 범위 안에선 에이전트가 문자 매칭으로 정밀 탐색**하는 2단 구조 (Claude Code 가 저장소에서 grep 으로
  잘 찾는 것도 범위가 좁아서) ② 의미 검색의 약점은 "주제가 비슷한 엉뚱한 것(거짓 친구)" — 같은 주제의 방해 문서가 많을수록 ③ 검색 비교는 하네스·전달 방식과
  **묶어서** 평가해야 한다 (같은 모델 Opus: 자체 하네스 93.1 vs Claude Code 76.7)
- **믿어도 되는 결과:** 바로 넣기 방식에서 10개 모델·하네스 조합 **모두** grep > 벡터 (표 1). 저자가 일반화하지 않음을 명시(5장).
- **해석에 주의할 결과:**
  - 과제 특성 — 답의 근거가 글자 그대로 있는 대화 기억(날짜·횟수·선호). 교차 언어·바꿔 말한 문서·코드 의미에선 다를 수 있다 (저자 명시)
  - 자체 하네스 Chronos 는 **도구 루프 전에 벡터 상위 15개를 첫 컨텍스트로 넣는다**(3.3.1) — grep 전용 조건에서도 껐는지 명시 없음 → 그렇다면 "grep 93.1"은 벡터로 시작한 혼합
  - 파일 전달 방식에선 10개 중 5개에서 벡터가 앞섬, Codex+GPT-5.4 grep 93.1 → 55.2 붕괴
  - 범위가 작을 때(실험 2, 세션 5개) 자체 하네스에선 벡터가 더 높음 (87.9~94.0 vs 83.2~89.7). 방해 세션을 설정마다 다시 뽑아 곡선이 들쭉날쭉
  - 116문항, 실행 1회로 보임 (반복·분산 보고 없음), Codex 일부 행 미완 (저자 명시)
- **읽는다면:** 3장(범위·도구 구현), 4.1.4 와 4.2.4 의 논의, 5장 한계.

## 한 줄 요약
한 사람의 대화 기록 안에서 답을 찾는 과제에서, 에이전트가 정규식을 만들어 쓰는 grep 이 벡터 검색보다 대체로 정확했지만, 결과를 파일로 넘기거나 하네스를 바꾸면 순위가 뒤집혔다.

## 왜 문자 매칭이 이겼나
1. 과제가 원문 그대로의 문자열(날짜·횟수·선호)을 요구 — 자기 대화에 대한 질문이라 질문 단어가 원문에 있을 확률이 높음 (4.1.4)
2. 검색어를 에이전트가 만들고 실패하면 바꿔 다시 시도 → 실제로는 "LLM 이 반복해 다듬는 문자 매칭". 변별력 있는 문자열을 찾으면 매우 정밀, 못 찾으면 0 (4.1.4)
3. 벡터는 같은 사람·비슷한 주제의 방해 세션을 상위로 끌어옴 (4.1.4, 4.2.4)
4. 범위가 작아 grep 은 매칭을 전부 반환, 벡터는 상위 k 만 (내 해석)
5. 전처리가 흩어진 시간 표현을 정규화된 이벤트 문자열로 만들어 둠 (3.2.1)

## ⚠ 실험 1 과 실험 2 의 같은 조건 결과가 어긋남 (2026-11-15, 표 1 vs 표 2·3 'full' 열 직접 대조)
같은 조건(전체 대화 기록, 바로 넣기)인데:
| 모델 / 하네스 | 실험1 grep/벡터 | 실험2 full grep/벡터 | 이긴 쪽 1→2 |
|---|---|---|---|
| Opus / Chronos | 93.1 / 83.6 | 89.7 / 92.2 | grep → 벡터 |
| Opus / Claude Code | 76.7 / 75.0 | 94.0 / 72.4 | grep → grep (grep +17) |
| Haiku / Chronos | 83.6 / 76.7 | 83.6 / 87.9 | grep → 벡터 |
| Haiku / Claude Code | 55.2 / 44.0 | 81.9 / 44.0 | grep → grep (grep +27) |
| GPT-5.4 / Chronos | 89.7 / 81.9 | 78.5 / 82.8 | grep → 벡터 |
| Gemini Pro / Chronos | 91.4 / 82.8 | 86.6 / 84.5 | grep → grep |
| Gemini Pro / Gemini CLI | 81.9 / 75.0 | 78.5 / 89.7 | grep → 벡터 |
| Flash-Lite / Chronos | 86.2 / 62.9 | 89.2 / 83.6 | grep → grep (벡터 +21) |
| Flash-Lite / Gemini CLI | 87.1 / 67.2 | 70.7 / 74.1 | grep → 벡터 |
→ 실험 2 에선 **9개 중 5개에서 벡터 우세**, 같은 설정 점수 차 최대 27점. 논문 설명 없음. 실행 간 편차든 설정 차이든 **"grep 이 일관되게 더 정확"은
논문 자체 데이터로도 뒷받침 안 됨**. 1회 실행 비교의 한계 (Rethinking MAS 의 "편차 ≈ 효과"와 같은 문제).

## 비판적 검토
- 결론은 일부(원문 그대로의 근거가 있는 작은 범위)에서만 성립 — 저자·HN 모두 인정
- 그 일부도 **grep 쪽으로 기운 조건** (조작이라기보다): 질문별 작은 전용 파일(세션 39~66) / 글자 그대로의 근거 /
  **시간 표현을 정규화 문자열로 미리 뽑음**(Chronos 전처리 = "찾기 쉽게 정리하기") / **벡터 쪽 임베딩 모델·재정렬기 미기재**(3.2.3 — 기준선 강도 판단 불가) /
  자체 하네스 Chronos 인용(Sen et al., 2026)의 제1저자 = 이 논문 제1저자
- 반대 사정: LongMemEval 은 기존 표준 벤치마크, 같은 전처리를 벡터에도 줌, 작은 범위에선 벡터가 이긴 설정도 있음
- **실무 이전성:** 질문별 작은 묶음이 없음(실무 RAG 는 수백만 청크 규모), 다국어·바꿔 말하기·버전 혼재 → 먼저 **좁히기(인덱스·메타데이터)와 정리하기(정규화·묶기)** 가 필요.
  이 논문의 숨은 공로자는 전처리일 가능성. 가져갈 것 = "좁고 정리된 범위면 에이전트 문자 매칭이 정밀하다 → 실무의 일은 좁히기와 정리하기"

## 저자 주장
- 바로 넣기: 모든 조합에서 grep > 벡터. 차이 최대 Chronos+Flash-Lite 86.2 vs 62.9, 최소 Claude Code+Opus 76.7 vs 75.0 — 표 1
- 하네스 효과 ≈ 검색 방식 효과: Opus 자체 93.1 vs Claude Code 76.7 — 4.1.3
- 파일 전달은 "도구 메시지 읽기"를 "파일을 찾아 열고 통합하기"로 바꿔서, 그 단계가 약하면 검색 품질과 무관하게 무너진다 — 4.1.4
- 약한 모델(Haiku)일수록 grep–벡터 차이가 큼 — 반복 검색어 수정·재정렬 결과 읽기에 약해서라는 가설 — 4.1.4
- 방해 문서가 늘어도 두 방식이 나란히 떨어지지 않음. 작은 범위에선 벡터가 앞서다가 하네스·모델에 따라 grep 이 따라잡거나 역전 — 4.2.4
- Claude Code 는 모든 설정에서 grep 우세, Gemini CLI+Pro 는 모든 설정에서 벡터 우세 → 제공사 도구의 고유한 편향 — 4.2.4

## 관심 주제와의 연결
- **대규모·다국어 RAG:** 그대로 옮기기 어려움 — 교차 언어 검색에선 문자 매칭이 안 통한다. 옮겨 올 부분은
  "에이전트가 검색어를 다시 만드는 것"(예: 대상 문서의 언어로 다시 검색).
- **2단 구조:** 의미 검색으로 후보 좁히기 → 좁힌 범위에서 에이전트 문자 매칭. 문서 생성 에이전트의 자료 준비(검색으로 파일 선택 → 고른 파일 전문)도 같은 방향.
- **하네스:** 결과 전달 방식만으로 순위가 뒤집힘 — Meta-Harness 의 "하네스가 성능을 좌우한다"의 검색판. 정보 틀(쓰는 쪽이 골라 읽을 수 있나)과도 연결:
  파일 전달은 "접근 수단을 주는" 방식인데, 에이전트가 읽기·통합을 못 하면 오히려 손해.

# LLMs Corrupt Your Documents When You Delegate

- arXiv 2604.15597v1 · 발표 **2026-04-17** · cs.CL · 학회 미확인 · Philippe Laban, Tobias Schnabel, Jennifer Neville (Microsoft — HN·웹 기사 표기, HTML 확인 안 함)
  — LLMs Get Lost(2505.06120)와 같은 저자군
- 변환 html · 읽은 범위: 1~6장, 8~9장 (7장 관련연구 훑음, 부록 안 읽음)
- 정리 2026-11-15 KST

## 먼저 — 용어와 구조
- **위임(delegation):** 사용자가 결과를 일일이 검토하지 않고 LLM 에게 문서 작업을 맡기는 방식 (예: vibe coding). 검토 안 하니 "조용한 오류"가 문제.
- **DELEGATE-52:** 52개 전문 분야(코드·결정학·악보·회계·레시피·자막 등) × 분야당 작업 환경 6개 = 310개.
  환경 = 실제 문서 1개(2~5k 토큰) + 편집 과제 5~10개 + 방해 문서(관련은 있지만 불필요한 문서 8~12k 토큰).
- **왕복(round-trip) 평가:** 편집 과제마다 정방향 지시와 역방향 지시를 짝으로 둔다 (예: 장부를 비용 분류별 파일로 나누기 ↔ 다시 시간순 한 파일로 합치기).
  완벽한 모델이면 원본으로 돌아온다 → **정답 없이** "원본과 얼마나 같은가"로 채점. 왕복 10번 = 상호작용 20회를 이어 붙여 긴 작업 흐름을 흉내.
- **채점:** 분야마다 파서를 만들어 문서를 구조로 바꾼 뒤 비교 (레시피 = 재료·단계·팁, 가중치 40/40/20). 200g→800g 같은 의미 변화는 크게,
  200g→0.2kg 같은 표면 변화는 무시. 일반 유사도·LLM 판정(GPT 5.4)은 이 지표 분산의 최대 25% 밖에 설명 못 함 (부록 C 요약).

## 결론
**문서 작업을 LLM 에게 맡기면 최고 모델도 20번 편집 후 내용의 약 25%가 망가진다. 원인은 조금씩 쌓이는 오류가 아니라 가끔 터지는 큰 오류이고,
문서가 길수록·오래 할수록·불필요한 문서가 섞일수록 곱으로 나빠진다. 기본 도구(파일 쓰기·코드 실행)를 줘도 나아지지 않았다.**
- **가져갈 것 (문서 생성·편집 에이전트):**
  ① **평균이 아니라 큰 오류를 잡는 감시** — 열화의 약 80% 가 한 번에 10점 이상 떨어지는 "치명적 오류"에서 옴 → 단계마다 구조 비교(diff)로 급락을 잡아 되돌리기
  ② **강한 모델은 지우기보다 바꾼다** — 약한 모델은 내용 삭제, 최상위 모델은 있는 내용을 틀리게 바꿈 → 개수 확인만으론 부족, 값·내용 대조 필요
  ③ **같은 문서를 LLM 이 여러 번 다시 쓰게 하지 말 것** — 문서 크기와 횟수가 곱으로 작용 (1k 토큰당 손실: 2회 후 0.7% → 20회 후 3.6%)
  ④ **전역 재구성(나누기·합치기·분류)이 제일 위험**, 국소 편집(문자열 수정·참조)은 안전 → 큰 재구성은 코드로, LLM 은 국소 편집으로 나누기
  ⑤ **방해 문서를 줄여라** — 처음엔 차이가 0.4~4% 지만 20회 후 2~8% 로 커짐 → 검색 정밀도가 긴 작업에선 누적
  ⑥ **짧은 평가로 판단하지 말 것** — 2회 후 같던 두 모델(91.5 vs 91.1)이 20회 후 48.3 vs 64.1
  ⑦ **무결성 채점은 LLM 판정 대신 구조 파싱 + 규칙 비교** — "숫자·출처는 LLM 말고 코드로 대조"하는 설계와 같은 방향
- **믿어도 되는 결과:** 19개 모델 전부 열화(평균 50%, 최상위 3개 25%), 분야 52개 중 최상위 모델이 "준비됨"(20회 후 98% 이상)인 건 11개,
  Python 만 대부분 모델이 무손실(17/19). 정답 없이도 채점되는 설계라 규모가 크다.
- **해석에 주의할 결과:**
  - "도구가 도움 안 됨"은 **저자도 최적화 안 됐다고 밝힌 기본 ReAct 하네스** 기준 (도구 8~12회, 입력 토큰 2~5배). 모델이 코드 실행보다 파일 통째 쓰기를 선호한
    탓도 큼 — 좋은 하네스(패치 단위 편집 + 보존 검사)에선 다를 수 있다
  - 왕복 평가는 정방향·역방향 오류를 구분 못 한다 (HN 지적: "역방향에서 더 틀리는 것 아닌가"). 역방향(합치기 등)이 더 어려운 과제일 수 있음
  - 각 상호작용은 독립 단일 턴 세션 — 실제는 멀티턴이라 더 나쁠 것이라고 저자 주장 / 편집이 되돌릴 수 있어야 해서 생성·소통 업무는 범위 밖
- **읽는다면:** 2.1절(왕복 평가), 4.2절(도구 사용), 5장(치명적 오류·삭제 vs 변조·작업 유형), 6장.

## 한 줄 요약
52개 분야의 실제 문서를 19개 LLM 에게 20번 편집시키니 최고 모델도 약 25%를 망가뜨렸고, 그 대부분은 가끔 터지는 큰 오류였으며 도구를 줘도 나아지지 않았다.

## 저자 주장
- 모든 모델 열화, 20회 후 평균 −50%. 최상위: Gemini 3.1 Pro 80.9, Claude 4.6 Opus 73.1, GPT 5.4 71.5 — 표 1
- 조건의 80% 이상에서 20점 이상 열화. Python 만 17/19 모델 무손실. Gemini 3.1 Pro 는 52개 중 11개 분야에서 "준비됨" — 표 2
- 짧은 평가는 긴 평가를 예측 못 함 (GPT 5 vs Kimi K2.5: 2회 91.5 vs 91.1 → 20회 48.3 vs 64.1) — 4.1절
- 기본 에이전트 하네스(파일 읽기·쓰기·코드 실행)에서 4개 모델 모두 도구 없을 때보다 나쁨, 평균 추가 열화 6%. 도구 8~12회, 입력 토큰 2.0~4.6배.
  좋은 모델일수록 코드 실행 비중이 큼 (GPT 4.1 10% → GPT 5.4 45%) — 4.2절, 표 3·4
- 문서 크기 1k → 10k 토큰: GPT 5.4 20회 후 91.4 → 59.9. 1k 토큰당 손실이 2회 후 0.7% → 20회 후 3.6% (약 5배) — 크기와 횟수는 곱으로 작용 — 4.3절
- 100회까지 늘려도 정체 없이 계속 하락 (GPT 5.4 58.7) — 4.4절
- 방해 문서 제거 시 2회 후 +0.4~4%, 20회 후 +2~8% — 4.5절
- 이미지 편집 모델은 훨씬 심함 (최고 28~30%) — 4.6절
- 열화의 약 80% 는 한 번에 10점 이상 떨어지는 치명적 오류. 강한 모델은 작은 오류를 더 잘 피하는 게 아니라 치명적 오류를 늦추고 덜 낸다 — 5장, 표 9
- 약한 모델은 삭제, 최상위 모델은 변조가 주원인 — 5장, 그림 7
- 코드·구조화된 분야가 쉽고 자연어·희귀 어휘 분야가 어렵다. 전역 재구성(나누기·합치기·분류)이 국소 편집보다 어렵고, 여러 작업을 조합하면 더 어렵다 — 5장
- GPT 4o → GPT 5.4 (16개월) 14.7 → 71.5 로 빠르게 개선 중 — 6장

## 실험에서 볼 것
- 정답이 필요 없는 왕복 평가 + 분야별 파서라 52개 분야로 확장 가능. 지시를 실제로 수행했는지(아무것도 안 하고 되돌리기 같은 꼼수) 부록 A 에서 확인했다고 함 (안 읽음).
- 편집 과제가 10개 미만이면 순서를 섞어 반복 — 같은 과제 반복보다 열화가 크다고 부록 D (안 읽음).
- 도구·크기·길이·방해 문서 실험은 GPT 계열 일부 모델만.
- 분야별 가중치는 저자가 절제 실험으로 맞춤 (부록 K.2, 안 읽음).

## 한계
- 논문이 밝힌 것: 단일 턴 세션(멀티턴이면 더 나쁠 것) / 문서 크기·방해 문서·횟수는 비용 때문에 실제보다 작게 / 되돌릴 수 있는 편집만, 구조화된 분야 유리.
- 읽으며 본 것 (내 판단): 왕복 평가는 "정방향 결과가 쓸 만한가"를 직접 재지 않는다 — 정방향이 틀려도 역방향에서 우연히 복원되면 감점이 없고,
  정방향은 맞았는데 역방향(합치기)에서 틀려도 감점. 실무 위임은 대부분 정방향만 한다. / 하네스가 기본형이라 "도구 무용"은 일반화 어려움.

## 근본 원인 (부록 A·B·E·F 추가로 읽음)
- **정보는 제대로 줬나 → 대체로 그렇다.** 단일 턴 완전 명세, 정답 경로가 하나인 편집만(B.3). 단계의 93.8% 가 전부/일부 수행, 붕괴 구간(<20)에서도 82% 는
  시도했는데 틀림 — LLM 판정(GPT 5.4) 기준(A). LLMs Get Lost 와 달리 정보 부족이 원인 아님.
- **숨은 엄격 조건:** 각 편집은 이전 기록 없는 독립 세션 → 역방향 때 원본을 못 봄. 되돌릴 수 없는 편집은 "원래 순서를 original_order.csv 에 기록하라"는
  장부 기법으로 가역화(B.3) → 되돌릴 정보를 **모델이 스스로 보존**해야 함. 실무(원본을 버전 관리로 보존)보다 엄격할 수 있음.
  부분 수행 16.7% → 점수 과대평가 가능성(저자 언급).
- **데이터가 보인 원인:** 실행 오류 / 열화의 80~98% 가 한 번에 10점+ 치명적 오류(E) / 오류 유형: 환각·구조 변경·역방향 일부 건너뜀·문법·계산·중복·재정렬·
  템플릿식 채우기·손실·잘림(F) / 앞 오류로 뒤 지시가 수행 불가(붕괴 구간 8%).
- **내 추론 (논문이 직접 말하지 않음):** 핵심 메커니즘은 **매번 문서 전체를 다시 생성**하는 작업 방식 — 복사 보장이 없어 안 바꿀 부분도 토큰을 다시 만들다
  가끔 덩어리 누락·축약·값 변경. 정합 근거: 크기×횟수 곱 / 전역 재구성이 가장 어려움 / 좋은 모델일수록 코드 실행(10→45%) / Python 이 가장 안전.
- **대책:** 원본·이력은 LLM 밖에 보존(버전 관리) · 통째 재작성 대신 패치 · 편집 전후 구조 diff 로 급락 감지.

## 관심 주제와의 연결
- **문서 생성·편집 에이전트:** 생성 자체보다 **수정·재생성 루프**(사람의 수정 요청 반영, 여러 번 다듬기)에 그대로 해당. "같은 문서를 여러 번 다시 쓰게 하지 말 것",
  "전역 재구성은 코드로", "단계마다 구조 diff 로 급락 감지", "숫자·출처는 코드 대조"가 바로 쓸 수 있는 설계 규칙.
- **평가 설계:** 정답 없는 평가를 **왕복 + 구조 파싱**으로 만든 사례 — 생성 에이전트 평가(정답이 여럿인 문제)의 한 해법. LLM 판정이 구조 지표 분산의 25% 만
  설명했다는 것도 "규칙 검사로 바꾼" 판단의 근거.
- **정보 틀과의 연결:** 방해 문서의 해악이 횟수에 따라 누적 → "목적 밖의 정보 = 잡음"이 긴 작업에서 곱으로 커진다는 근거.
- **LLMs Get Lost 와 같은 저자·같은 구조:** 평균 하락의 실체는 "가끔 크게 틀림"(저쪽: 편차, 이쪽: 치명적 오류), 짧은 평가로는 안 보임.
- **하네스:** "기본 도구 하네스는 오히려 나쁨" + "좋은 모델일수록 코드 실행" → 편집 도구 설계(패치 단위, 보존 검사)가 개선 여지. Harness Design 실증 연구와 같이 볼 것.

# paper-post — 정리한 것을 글로

글의 재료는 이미 검증해 둔 것만 쓴다: notes 의 **결론 블록**(판정·가져갈 것·믿어도 되는 결과·해석에 주의할 결과), 외부 평가 표,
ideas 의 원리. 글을 쓰면서 새 사실을 더하지 않는다 — 더 필요하면 먼저 paper-read 로 notes 를 보강한다.

## 시작
```bash
python -m paper_analyst.profile          # 출력 언어(reader.language)·관점(reader.lens)
```

## 흐름
1. **재료 모으기** — 대상 논문의 `library/papers/<id>/notes.md` 결론 블록과 외부 평가, 관련 ideas.
   서재 연결(후속·반박·같은 방향)이 있으면 함께 엮을지 묻는다 — 두세 편을 한 흐름으로 묶은 글이 한 편 요약보다 읽힌다.
2. **각도 한 번 묻기** — "무엇을 말하는 글인가" 한 문장 (예: "LLM 판정기는 정확도 한 숫자로 고르면 안 된다").
   사용자가 정하지 않았으면 결론 블록에서 2~3개 후보를 제시하고 고르게 한다.
3. **초안 쓰기** — `posts/<YYYY-MM-DD>_<짧은-영문-이름>/`
   - `meta.json` : `{"title": "...", "sources": ["<arXiv id>", "ideas/<파일>"], "created": "<YYYY-MM-DD>"}`
   - `linkedin.md` : 본문 1,300자 안팎(한도 3,000). **첫 줄이 훅** — '더 보기' 전에 보이는 약 210자 안에 주장 전체가 들어가게.
     구조: 훅(주장) → 논문이 보인 것 2~3줄(수치는 조건과 함께) → 그래서 실무에서 → 한계 한 줄 → 출처(arXiv 링크) → 해시태그 3~5개.
     마크다운은 굵게·목록 정도만 (화면이 기호를 걷어낸 글자로 복사한다)
   - `blog.md` : 장문. 제목 → 문제 → 논문이 보인 것 → 믿어도 되는 결과 / 해석에 주의할 결과 → 적용한다면 → 출처.
     표는 마크다운 표로 (티스토리용 HTML 은 화면이 변환한다)
4. **점검** — `python -m paper_analyst.post check posts/<이름>` → 경고가 있으면 고치고 다시 돌린다.
5. **보고** — 초안 경로, 각도 한 문장, 점검 결과. 게시는 사람이 화면의 **발행** 탭에서 한다 (복사, 또는 LinkedIn 은 확인 창을 거치는
   게시 버튼). 이 세션에는 게시 권한이 없다 — "올려줘"라고 해도 직접 올리지 말고 발행 탭을 안내한다.

## 쉽게 읽히게 — 용어·비유·밀도

독자는 이 분야 사람이 아닐 수 있다. 다 읽고 **기억에 남을 문장 하나**를 쓰기 전에 정하고, 그 문장이 쉽게 닿게 쓴다.

**용어 — 번역투·전문용어 대신 일상어**
- 예: "실행 간 편차" → "같은 질문에도 답이 매번 달라짐" / "멀티턴" → "여러 번 주고받는 대화" /
  "신뢰도" → "매번 비슷한 품질이 나오는지" / "하네스" → "AI 를 감싼 작업 틀(지시문·도구·기억 관리)"
- 꼭 써야 하는 용어(논문 제목, 이름이 붙은 개념)는 처음 나올 때 한 번만 풀어 준다. 영어 원어는 필요할 때만 괄호로.
- 우리 메모에서만 쓰는 이름표(예: "씨앗·증폭")는 그대로 쓰지 않고 풀어서 쓴다.

**비유 — 쉬운 것보다 맞는 것**
비유의 기준은 "쉽고 친숙한가"가 아니라 **논문에서 실제로 일어난 일과 구조가 같은가**다. 친숙하지만 구조가 다른 비유는
독자에게 틀린 그림을 남긴다.
1. 먼저 notes 에서 **논문이 보인 일의 핵심 특징을 3~5개** 적는다 (무엇이 어떤 순서로 오나, 무엇을 할 수 있었는데 안 했나,
   조건을 바꾸면 어떻게 되나).
2. 업계 밖 일상 후보를 2~3개 떠올리고, 특징마다 맞음 / 덜 맞음 / 틀림을 표로 대조한다.
3. **틀림이 하나라도 있으면 버린다.** 특히 비유가 원래 없는 성질을 덧붙이지 않는지 본다 — 이게 가장 놓치기 쉽다.
4. 보고할 때 이 대조표를 함께 보여 준다 (사용자가 비유를 판단할 수 있게).

실제로 걸러진 예 (LLMs Get Lost — 요구가 여러 번에 나눠 옴 · 빈칸을 추측으로 채운 완성본을 일찍 냄 · **고칠 수 있는데도**
앞 답에 덧붙여 감 · 한 번에 다 주면 회복):
| 후보 | 버린/고른 이유 |
|---|---|
| 주문을 다 듣기 전에 요리를 시작한 주방 | 버림 — 주문은 보통 한 번에 들어온다. "나눠 옴"이 성립하지 않음 |
| 요구를 다 듣기 전에 벽부터 허문 인테리어 | 버림 — 허문 벽은 정말 못 되돌린다. "고칠 수 있는데 안 고침"이 "고칠 수 없었음"으로 바뀜 |
| 다 듣기 전에 일정부터 꽉 채운 여행 계획 | 고름 — 나눠 옴 · 추측으로 꽉 채움 · 다시 짤 수 있는데 끼워 넣음 · 다 들었으면 다른 일정, 모두 맞음 |

- 핵심 주장 하나에 비유 하나. 두 개 이상 넣지 않는다.
- 같은 비유로 "논문이 본 것"과 "읽고 든 생각"을 이어 가면 기억에 남는다 (예: 일정을 꽉 채운 친구 → 들은 만큼만 정해 두기).
- 비유는 이해를 돕는 장치이지 근거가 아니다. "논문이 본 AI 가 딱 이랬습니다"처럼 같다고 단정하지 말고 "이와 비슷했습니다".

**말투 — 인사이트는 인사이트답게**
- 논문이 확인한 것은 사실로, 우리가 읽고 정리한 것은 **"읽고 든 생각"**으로 쓴다. 시험하지 않은 생각을 "해법"·"이렇게 하라"(지시형 목록)로
  쓰면 검증된 처방처럼 읽힌다 → "~하면 덜 흔들릴 것 같습니다", "~하지 않을까 싶습니다" 같은 생각의 말투.
- 첫 줄도 같다: 논문 관찰은 단정해도 되지만, 거기서 끌어낸 결론은 "~라는 생각이 들었습니다"처럼 해석임이 보이게.
- 대상을 깎아내리는 말을 쓰지 않는다 ("섣불리", "멍청하게", "엉터리"). 무엇을 했는지 중립적으로 ("짐작으로 채운 답").
- "끝까지", "항상", "절대" 같은 전칭은 논문이 그렇게 보였을 때만. "원인 1위"처럼 순위·비중도 notes 에 근거가 있을 때만.
- "읽고 든 생각"은 재료로 쓴 ideas 의 핵심 주장 그대로 쓴다. 쓰다 보면 흔한 조언("확인하세요", "여지를 두세요")으로
  미끄러지기 쉽다 — 쓰고 나서 ideas 파일의 한 줄 요약과 같은 말인지 대조한다.

**밀도 — 휴대폰 화면에서 읽힌다고 생각하고**
- 문단은 1~3줄, 한 문단에 한 생각, 블록 사이 빈 줄.
- 목록은 블록당 3~4개, 항목은 한 줄(약 60자) 안팎. 괄호 안에 괄호를 넣지 않는다.
- 숫자는 한 문장에 1~2개. 실험 조건이 길면 따로 한 줄로.
- 소제목은 3~4개까지. 쓰고 나서 한 번 소리 내 읽듯 훑어, 막히는 단어와 긴 문장을 고친다.

## 지킬 것 (왜)
- **`*.private.md` 내용을 글에 옮기지 않는다** (회사·업무·경력·동료·큐레이터 맥락). 사용자가 이 대화에서 "내 경험을 넣어줘"라고
  명시하면 그 부분만 사용자 말로 쓰고, 비공개 파일 문장을 그대로 옮기지 않는다. 점검 도구가 겹치는 줄을 잡는다.
- **수치는 notes 에 있는 것만, 조건과 함께** ("7개 judge × 6개 벤치마크에서"). 저자 주장과 외부 평가를 섞지 않는다.
- **근거 강도를 숨기지 않는다** — 1회 실행·작은 표본·저자 자체 하네스 같은 한계는 한 줄이라도 쓴다. 과장한 훅은 신뢰를 잃는다.
  모델을 실험한 논문이면 **실험한 모델이 언제 모델인지**도 적는다 (예: "2025년 상반기 모델 — 최신 모델에서는 따로 확인 필요").
- **논문 그림·표를 복사하지 않는다** (저작권). 필요하면 수치를 인용하고 출처를 단다.
- 사람·회사 실명(논문 저자 소속 제외)을 쓰지 않는다. 큐레이터를 언급할 때도 실명 대신 "읽은 정리 글" 정도로.

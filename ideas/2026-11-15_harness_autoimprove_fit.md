# 에이전트에게 정보를 어떻게 줄 것인가 — 틀과 항목

> 2026-11-14~15 KST. 출발점: Meta-Harness (2603.28052, 2026-03-30) — `library/papers/2603.28052/notes.md`
> 근거 표기: 본문 = 이번에 읽은 본문, 초록 = 초록만 확인. 사례 판단은 논문 조건을 적용한 판단.

## 0. 틀 — 정보는 쓰는 쪽의 목적에 맞춘다
> **목적(내려야 할 결정)이 정한다: 필요한 범위(양) · 필요한 자세함(해상도) · 그 밖의 것 = 잡음.**
> **저장과 제시는 분리한다.**

- 새 원리는 아님(정보의 가치는 결정에 상대적 / 원본 보존·용도별 뷰). 법칙이 아니라 **이해와 범위 정의를 위한 틀**:
  모순처럼 보이는 주장을 정리하고, 설계 질문을 주고, 실험 변수(양·해상도·잡음 제거)를 정한다.
- **설계 질문:** 이 정보를 쓰는 쪽은 누구고 어떤 결정을 내리나? 그 결정에 필요한 범위와 자세함은? 스스로 찾아 읽을 수 있나?
- **잡음은 목적에 상대적:** 예전의 틀린 시도는 원인 분석엔 신호, 다음 행동 결정엔 오염원.

## 1. 틀에서 나온 규칙 (경험칙 — 논문 대여섯 편, 설정 제각각)
| 규칙 | 근거 |
|---|---|
| 1. 저장과 제시를 분리 — 원본 보존, 쓰는 쪽에 따라 가공 | Meta-Harness(원본, 본문) vs SkillRL·Trace2Skill(가공, 초록)·SWE-MeM(압축, 본문) |
| 2. 잡음은 목적에 따라 다름 | Meta-Harness 는 실패 기록으로 원인 분석(본문) / LLMs Get Lost 는 옛 오답이 작업 오염(본문) |
| 3. 필요 이상 많으면 해로움 | few-shot 32개 초과 시 9개 중 7개 하락(Meta-Harness 표 5) · 스킬 ≤3모듈이 큰 묶음보다 나음(SkillsBench 초록) |
| 4. 스스로 탐색 가능한 쪽엔 내용 대신 접근 수단 | Meta-Harness 파일시스템·조회 CLI — 반복당 82개 파일만 골라 읽음(본문) |

## 2. 쓰는 쪽별로 — 분석하는 에이전트 vs 작업하는 에이전트
| | 분석하는 에이전트 (하네스·스킬을 고치는 쪽) | 작업하는 에이전트 (과제를 푸는 쪽) |
|---|---|---|
| 결정 | 왜 실패했나, 무엇을 바꿀까 | 다음에 무엇을 할까 |
| 양 | 많이 — 여러 실행을 **비교**해야 원인이 보임 (이전 후보 20개+) | 필요한 만큼만 — 요구사항은 전부, 옛 시도는 제외 |
| 해상도 | 높게 — 원본 (LLM 요약은 손해: 원본 50.0 vs 요약 34.9 vs 점수만 34.6) | 관련 부분만 높게 — 아직 필요한 코드는 유지, 나머지 압축 (SWE-MeM) |
| 주는 방식 | 접근 수단 (파일, 조회 도구) | 골라서 넣기 (압축, 스킬 문서, 통합된 요구사항 — Concat 95%) |
| 사례 | Meta-Harness | SWE-MeM, LLMs Get Lost, SkillRL·Trace2Skill |

- 가벼운 정제(명백한 잡음 제거, 긴 출력 자르기, 찾기 쉬운 구조)는 **과제별 실험 영역** — 논문이 비교한 건 "LLM 요약 vs 원본"뿐.
  논문 안에도 원본을 해치지 않는 정리는 들어 있음 (도구 출력 30KB 제한, 조회 CLI 권고).
- Trace2Skill 은 둘을 잇는 구조로 보임: 원본 분석 → 스킬 문서로 증류 → 작업 에이전트에게 (초록 기준, 본문 확인 전).

## 3. 하네스 자동 최적화 — 언제 맞나
**하네스** = 모델 가중치 바깥에서 모델 호출을 감싸고, 매 단계 모델이 무엇을 보고·무엇을 할 수 있고·결과가 어떻게 이어지는지 정하는 코드
(입력 구성 · 검색 · 상태/메모리 · 도구 · 제어 흐름 · 출력 처리). 모델 + 하네스 = 에이전트. "평가 하네스(lm-evaluation-harness)"는 다른 뜻.

**Meta-Harness 방식:** 후보 하네스를 *평가 세트로 돌릴 때* 코드·점수·원본 실행 기록을 파일 구조로 남기고, 코딩 에이전트가 골라 읽으며
하네스 코드를 고친다. 실서비스 기록은 정답이 없어 그대로는 못 씀 → 실패 사례에 정답을 붙여 탐색 세트로.

**한 줄 기준:** 하네스가 좋아졌는지를 *사람 없이, 싸게, 여러 번 돌려도 같은 결론으로* 판정할 수 있는가.

성립 조건: ① 자동 채점 + 믿을 만함 ② 빠르고 쌈 (후보 ≈60 × 탐색 세트 50~100) ③ 실행 간 편차 < 기대 향상
④ 탐색 세트와 확인 세트 분리 ⑤ 기준선이 아직 틀리는 문제 충분 ⑥ 평가 중 사고 없음 (샌드박스·모의 환경)

| 적절 | 부적절 / 주의 |
|---|---|
| 라벨 있는 분류·추출 | 정답 없는 생성물 품질 (판정기 편차·보상 해킹 → 후보당 반복 실행 + 판정기 사전 검증 필요) |
| RAG 검색 정책 + 근거 표시 평가셋 (recall@k) | 탐색 세트 = 최종 평가 세트 |
| Text-to-SQL + 실행 가능 DB | 한 번 평가가 오래 걸림 |
| 코딩 에이전트 + 테스트 | 부작용 있는 실제 환경 (결제·메일·운영 DB) |
| 모의 도구 상담 에이전트 + 검증된 판정기 | 분포가 계속 바뀜 · 기준선이 이미 거의 다 맞힘 · 다회 사용자 대화(시뮬레이터 편향) |


## 4. 진행 순서와 사람의 역할
1. **적합성 판단** — 3장의 한 줄 기준
2. **에이전트 관점의 설계** — 사람이 보기 편한 형태가 아니라 에이전트가 작업을 잘 수행할 형태로 (0~2장):
   기록을 원본 그대로 찾기 쉬운 형식으로 (JSON · 일관된 파일 이름 · 후보별 디렉터리 — 루프 없이도 디버깅에 쓸모),
   자동 채점 평가 세트 (기준선이 틀리는 것 위주, 확인 세트 분리), 검증 테스트, 평가 스크립트는 제안자 밖에
3. **사람은 루프 밖에서 전체 프로세스 점검·설계** — 평가 세트 분리, 채점 신뢰성, 스킬(목표·금지·산출물만, 진단 절차는 강제 안 함 —
   논문 기준 가장 큰 레버), 출발 하네스(사람이 만든 것), 최종 채택과 과적합 확인

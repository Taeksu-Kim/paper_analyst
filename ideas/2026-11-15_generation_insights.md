## 인사이트 (문서 생성 에이전트 설계 기준)

### 1. 나눠 쓰면 → 장 사이 일관성이 새 위험이 된다
- 근거: Lost in Stories (사실·시간 오류, 중간부 집중), Story2Proposal (사후 검증만 하면 구조 흐트러짐·표 누락·장 간 불일치)
- 설계: **모든 장이 공유하는 "계약"을 대화 밖에 둔다** — 핵심 수치, 날짜, 용어, 들어가야 할 표·그림 목록. 장마다 생성할 때 주입하고, 생성 후 장 사이를 대조.
  특히 **숫자·날짜(사실·시간)**와 **중간 장**을 집중 검사.

### 2. 계획은 두 층으로 — 전역은 고정, 세부는 진화
- 근거: ArcDeck (전역 약속 문서를 먼저 고정), AgentCPM-Report (세부 개요는 초안을 쓰면서 고치는 게 낫다 — 단 학습된 모델 기준)
- 설계: 목적·핵심 메시지·독자는 처음에 고정, 장 구성·세부 개요는 초안 후 수정 허용.

### 3. 오류의 진원지는 "합치는 단계"
- 근거: Who is the Agent to Blame (단일 문서 요약은 안전, 여러 근거를 합치는 오케스트레이터에서 오류의 84.7%)
- 설계: 근거 ID 를 **생성 끝까지 들고 다니게** 하고, 합치는 단계의 출력을 그 입력 대비로 검증. 단계별 국소 검증으로 어디서 틀렸는지 찾기.

### 4. 숫자는 대조를 넘어 재계산
- 근거: Data Journalist Agent (코드 검증기가 문장을 데이터에 대해 다시 실행)
- 설계: 원문 숫자 대조 다음 단계로 **파생 숫자**(합계, 증감률, 비율)를 코드로 다시 계산해 확인.

### 5. 평가를 먼저 만든다
- 근거: AutoSciRub (실행 전 채점 기준 → 안내·검증·표적 수정, 일관된 향상)
- 설계: 요청 + 자료 → "이 문서에 반드시 있어야 할 것" 원자 목록 → 생성 안내 + 생성 후 항목별 YES/NO + 빠진 항목만 수정.
  RAG 답변의 사실 단위 YES/NO 평가와 같은 구조 — **정답 없는 생성물 평가의 실무형 해법**. 하네스 자동 개선의 채점기로도 쓸 수 있음.

### 6. 수정은 가장 작은 범위만
- 근거: MemSlides (국소 수정), DELEGATE-52 (통째 재작성 시 크기×횟수로 훼손 누적)
- 설계: 수정 요청이 오면 영향받는 장·표만 다시 생성, 나머지는 그대로 두고 구조 diff 로 확인.

### 7. 싼 위험 신호 — 토큰 엔트로피 (가설)
- 근거: Lost in Stories (일관성 오류가 엔트로피 높은 구간에서 남)
- 설계: 로컬 서빙(vLLM 등)은 logprob 을 줄 수 있으니, 생성 중 엔트로피가 튀는 구간을 "검사 우선" 표시. **논문은 관찰만 했고 이걸 검출기로 쓴 건 아님 → 실험 필요.**

## 공통 방향
**나눠 쓰되, 전체가 지켜야 할 것(계약·약속·채점 기준)을 대화 밖 공유 상태로 고정하고, 합치는 단계와 숫자·날짜를 집중 검증하고, 수정은 국소로.**
— "상태를 대화 밖에"(범위 우선 설계)와 "목적이 정보를 정한다" 틀의 생성판.

## 근거 한계

- AgentCPM-Report 의 이득은 학습된 8B 모델 기준 — 하네스(번갈아 쓰기)만의 효과는 모름

- GUIDE 는 신호 매우 약함
